# Стиль кода KODES

Библиотека живёт рядом с OpenFOAM и говорит на его типах (`scalar`, `label`),
поэтому за основу взят стиль OpenFOAM, к которому добавлено то, чего в нём нет:
правила для ядер, для `__device__`-виртуальных классов и для файлов `.cu`/`.cuh`.

Правило одно на каждую сущность, без исключений «по вкусу». Все исключения,
которые всё-таки есть, перечислены поимённо в конце.

---

## 1. Имена

Стилей четыре, и каждый отвечает на свой вопрос — что это за сущность и когда у
неё появляется значение:

| Стиль | Что им называется | Читается как |
|---|---|---|
| `UpperCamelCase` | типы | «это тип» |
| `lowerCamelCase` | всё, что вычисляется в рантайме: функции, переменные, поля | «это значение» |
| `kUpperCamelCase` | константы времени компиляции | «это не изменится» |
| `UPPER_SNAKE_CASE` | макросы | «это препроцессор» |

Плюс пятый, `snake_case`, но только для имён файлов (см. §2) — так строка в
листинге каталога сразу отличается от имени класса.

Подробно:

| Что | Стиль | Примеры |
|---|---|---|
| Пространство имён | одно, всё внутри | `kodes` |
| Классы, структуры, enum | `UpperCamelCase` | `Balancer`, `SeulexDeviceResources`, `TypeEntry` |
| Параметры шаблона | `UpperCamelCase` | `Base`, `Derived`, `ODESystem` |
| Функции и методы | `lowerCamelCase`, глагол первым | `loadSystem()`, `scratchBytesPerThread()` |
| Ядра (`__global__`) | `lowerCamelCase` + суффикс `Kernel` | `solveKernel`, `fillKeysKernel` |
| Переменные и параметры | `lowerCamelCase` | `batchSize`, `realBatchSize` |
| Закрытые поля класса | `lowerCamelCase_` | `batchSize_`, `numOfKeys_` |
| Открытые поля класса | `lowerCamelCase`, без подчёркивания | `vectors`, `deltaTTry` |
| Локальные переменные | `lowerCamelCase`, **никогда** с подчёркиванием | `dfdy`, `kTarg` |
| Константы: `constexpr`, `__constant__` | `kUpperCamelCase` | `kSeulexMaxOrder`, `kSeulexStepSequence`, `kKeyCount`, `kNoBalancer` |
| Макросы | `UPPER_SNAKE_CASE` с префиксом `KODES_` | `KODES_BLOCK_SIZE`, `KODES_MAX_KEYS` |
| Имена в файле настроек и в словаре OpenFOAM | `lowerCamelCase` | `"stiffness"`, `"rhsNorm"`, `"threadsPerBlock"` |

### Почему у констант свой префикс

`k` — не украшение. Он отвечает на вопрос, который в этом коде задаёшь чаще
всего: «это значение прилетело откуда-то в рантайме или было известно при
сборке?» В `Seulex::step` рядом стоят `dtOpt` (заполняется по ходу шага) и
`kSeulexStepFactor3` (коэффициент из таблицы) — без префикса они выглядят
одинаково и читаются одинаково неправильно.

Он же снимает настоящую ловушку. У `Balancer` есть метод `usesDerivatives()`, а
у каждого наследника — своя `static constexpr bool` с тем же смыслом. Пока обе
назывались одинаково, константа наследника **скрывала** метод базового класса, и
`balancer->usesDerivatives()` внутри наследника означало не то, что кажется.
Теперь это `kUsesDerivatives` и `usesDerivatives()`, и спутать их нельзя.

### Макрос или константа

Макросом остаётся только то, что сборка вправе переопределить снаружи через
`-D`: `KODES_BLOCK_SIZE`, `KODES_BALANCER_BUCKETS`, `KODES_MAX_KEYS`,
`KODES_MEMORY_HEADROOM`. Всё остальное, что известно при компиляции, —
`constexpr`-константа: она подчиняется областям видимости, имеет тип и видна
отладчику. Порядок Seulex, например, был `#define kMaxx_ (12)`, а стал
`constexpr label kSeulexMaxOrder = 12`.

Сокращения не используются, кроме устоявшихся в предметной области: `ODE`,
`RHS`, `LU`, `MPI`, `Jac`, `Tol`. `numOfSystems`, а не `nSys`.

## 2. Файлы

| Расширение | Что это |
|---|---|
| `.cuh` | заголовок |
| `.cu` | единица трансляции |

`.cu` **никогда** не включается из `.cuh`. Раньше так делались шаблоны
(`Integrator.cuh` включал `Integrator.cu`); теперь шаблонов, требующих этого, в
библиотеке нет.

Имя файла:

* заголовок с **одним главным классом** называется по нему, `UpperCamelCase`:
  `Balancer.cuh`, `SeulexDeviceResources.cuh`;
* всё остальное — свободные функции, таблицы, константы, набор мелких
  сопутствующих типов — называется по тому, что даёт, `snake_case`:
  `basic_types.cuh`, `type_table.cuh`, `balancer_table.cu`,
  `seulex_constants.cu`.

По имени файла сразу видно, что внутри, и `ls` разделяется на две колонки сам
собой:

```
Balancer.cuh              balancer_table.cu
RHSNormBalancer.cuh       balancer_table.cuh
StiffnessBalancer.cuh
TemperatureBalancer.cuh
```

`snake_case`, а не `lowerCamelCase`, именно ради контраста: `balancer_table.cuh`
рядом с `Balancer.cuh` отличается одной заглавной буквой в начале, а
`balancer_table.cuh` видно с другого конца экрана.

Защита от повторного включения — `KODES_<ИМЯ_ФАЙЛА>` плюс `#pragma once`:

```cpp
#ifndef KODES_SEULEX_DEVICE_RESOURCES
#define KODES_SEULEX_DEVICE_RESOURCES

#pragma once
...
#endif
```

## 3. Каталоги

* `src/<Подсистема>` — `UpperCamelCase`, по имени подсистемы:
  `Balancer/`, `Integrator/`, `Resources/`, `Factory/`, `Settings/`, `ODESystem/`.
* Каталог заводится, когда в нём **больше двух** файлов. Каталог ради одного
  класса — лишний уровень в пути и лишняя строка `-I`.
* `examples/<кейс>` — `snake_case`, как и всё, что не является классом.
* Сгенерированный чужой код лежит отдельно и не переименовывается: выход pyJac
  в `data/mechanisms/` — его стиль не наш.

## 4. Разметка

Как в OpenFOAM:

* отступ — 4 пробела, табуляций нет;
* фигурная скобка на отдельной строке, включая `if`/`for` с одним оператором;
* длинный список аргументов — скобки на своих строках, по аргументу на строку;
* ширина — 80 столбцов для комментариев, до ~100 для кода;
* `*` и `&` прижимаются к типу: `scalar* y`, `const LaunchConfig& config`.

```cpp
__host__ size_t
Balancer::keyScratchBytesPerThread
(
    const label systemSize,
    const bool usesDerivatives
)
{
    if (!usesDerivatives)
    {
        return 0;
    }

    return size_t(systemSize) * sizeof(scalar);
}
```

## 5. Комментарии

Комментарий отвечает на «почему», а не «что» — «что» видно из кода. Пишется над
объявлением в заголовке, обычными предложениями, без `//!<` и без доксигеновской
разметки.

Особенно это касается мест, где код выглядит странно и это намеренно: порядок
copy-then-construct в фабрике, запрет трогать указатели в конструкторе,
приведение `DeviceResources*` вниз внутри `step()`. Такое место без объяснения
кто-нибудь «починит».

## 6. Правила, специфичные для CUDA

* **Ядра** — свободные функции в `kodes`, с суффиксом `Kernel`. Суффикс не
  украшение: он снимает столкновение между ядром и одноимённым методом, который
  его запускает (`Integrator::setDeltaT` и `setDeltaTKernel`), и в месте вызова
  сразу видно, что дальше запуск сетки.
* **Атрибуты** пишутся первыми, в порядке `__host__ __device__`.
* **Устройственные объекты** (класс, чьи виртуальные функции зовут из ядра)
  подчиняются контракту из `Factory/device_object.cuh` и отдают наружу ровно
  четыре статических метода: `create`, `destroy`, `createStub`, `destroyStub`.
  Имена именно эти — даже если класс, как `PyJacSystem`, пишет их сам, потому
  что его конструктор берёт не четыре размера. Подробности — в
  [`DeviceObjects_explained.md`](DeviceObjects_explained.md).
* **Стоимость в памяти** объявляется парой статических методов с одинаковой во
  всей библиотеке сигнатурой:
  `scratchBytesPerThread(systemSize, parameterSize)` и
  `stateBytesPerSystem(systemSize, parameterSize)`. Именно это позволяет одной
  таблице типов держать классы, у которых больше нет ничего общего.
* **Ошибки на хосте** — `fprintf(stderr, ...)` с `__FILE__`/`__LINE__` и
  `std::exit(EXIT_FAILURE)`. Исключения не бросаются наружу: единственное место,
  где они возникают (rapidjson в `Config`), ловит их и переходит на тот же
  способ. Проверять `cudaError_t` руками не нужно — есть `CUDA_CHECK` и
  `CUDA_CHECK_LAST`.
* **Индексация** делается только макросами `INDEXVEC`/`INDEXMAT` (scratch) и
  `INDEXSTATE` (state), не арифметикой на месте: перепутать шаг `GRID_DIM` и
  `batchSize` слишком легко, и ошибка проявится не там, где сделана.

## 7. Именованные исключения

Их четыре, каждое — совместимость с чужим кодом, а не вкусовщина:

1. `SMALL` и `GREAT` — макросы без префикса `KODES_`. Так они называются в
   OpenFOAM, и код, который читают вместе с моделью химии, называет их так же.
2. `INDEXVEC`, `INDEXMAT`, `INDEXSTATE`, `T_ID`, `GRID_DIM` — тоже без
   префикса. `INDEXVEC` обязан совпадать с макросом `INDEX`, который pyJac
   генерирует сам; переименование развело бы два имени для одной раскладки.
3. `scalar` и `label` — строчные имена типов. Это типы OpenFOAM, и переход к
   `Scalar`/`Label` сделал бы код, разделяемый с моделью химии, нечитаемым.
4. `src/ODESystem/grimech/`, `src/ODESystem/h2o2/` — выход pyJac. Он
   перегенерируется, править его руками нельзя.

## 8. Как добавить файл

1. Решить, класс это или набор инструментов, — от этого имя файла.
2. Защита от включения `KODES_<ИМЯ>` плюс `#pragma once`.
3. Если это устройственный объект — контракт из `device_object.cuh`, строка
   `KODES_DECLARE_DEVICE_OBJECT` в заголовке и `KODES_DEFINE_DEVICE_OBJECT` в
   `.cu`, плюс строка в таблице своей подсистемы.
4. Строка в `cmake/kodes.cmake` — и, если появился новый каталог, ещё и в
   `KODES_INCLUDE_DIRS` и в `Make/options` модели OpenFOAM.
