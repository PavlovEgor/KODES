# Как в KODES устроены абстрактные классы, живущие на GPU

Этот файл объясняет один-единственный паттерн, по которому в библиотеке сделаны
**все** классы, выбираемые в момент запуска программы: интегратор
(`IntegrationMethod` → `Seulex`, `Euler`), балансировщик (`Balancer` →
`TemperatureBalancer`, ...), хранилище (`DeviceResources` → `SeulexDeviceResources`,
...) и система уравнений (`ODESystem` → `PyJacSystem`).

Раньше эти механизмы работали по-разному: балансировщик был виртуальным объектом
на устройстве, интегратор — шаблонным параметром, то есть выбирался при
компиляции. Теперь у всех один паттерн, и весь он умещается в два заголовка:

| файл | что в нём |
|---|---|
| `src/Factory/device_object.cuh` | как **построить** такой объект (одинаково для всех) |
| `src/Factory/type_table.cuh`    | как **выбрать по имени**, какой именно строить |

Дальше — почему всё именно так, а не проще.

---

## 1. В чём, собственно, сложность

Мы хотим написать обычную вещь:

```cpp
kodes::Balancer* balancer = ...;      // какой именно — решаем при запуске
balancer->key(...);                   // виртуальный вызов
```

но `key()` вызывается **внутри CUDA-ядра**, то есть на устройстве. И тут обычный
C++ ломается о три вещи подряд.

### 1.1. Таблица виртуальных функций у хоста и у устройства — разные

У объекта с виртуальными функциями первым полем лежит указатель на vtable —
таблицу адресов этих функций. Адреса хостового кода и адреса кода на устройстве
живут в **разных адресных пространствах**. Значит:

```cpp
kodes::StiffnessBalancer b(...);          // сконструирован на хосте
cudaMemcpy(devPtr, &b, sizeof(b), ...);   // скопирован на устройство
someKernel<<<...>>>(devPtr);              // ядро зовёт devPtr->key(...)
```

не работает: в скопированных байтах лежит **хостовая** vtable, и ядро уйдёт по
адресу, которого на устройстве нет.

Вывод: объект обязан быть **сконструирован на устройстве**, чтобы конструктор
записал в него устройственную vtable. Делается это `placement new` внутри ядра:

```cpp
template<class T>
__global__ void constructDeviceObjectKernel(T* object, ...)
{
    new (object) T(...);        // конструктор выполняется на устройстве
}
```

### 1.2. Но буферы выделяет хост

`cudaMalloc` вызывается с хоста. Значит, адреса буферов рождаются на хосте, а
записать их надо в поля объекта, который лежит в памяти устройства и с хоста
разыменован быть не может.

Отсюда **host stub** — двойник объекта на хосте:

```
   ХОСТ                                        УСТРОЙСТВО
   ┌──────────────────────┐                    ┌──────────────────────┐
   │ hostStub             │                    │ devObject            │
   │  vtable  → хостовая  │                    │  vtable  → устройств.│
   │  batchSize_ = 1000000│                    │  batchSize_ = 1000000│
   │  keys_   ────────────┼──── cudaMalloc ───▶│  keys_   ────────────┼──▶ буфер
   │  order_  ────────────┼──── cudaMalloc ───▶│  order_  ────────────┼──▶ буфер
   └──────────────────────┘                    └──────────────────────┘
```

Стаб — это «бланк», который хост заполняет адресами, а потом целиком, байт в
байт, отправляет на устройство.

### 1.3. Порядок этих двух действий важен, и он неочевиден

```
1) cudaMalloc(&devPtr, sizeof(T))     место под объект на устройстве
2) hostStub->allocate()               хост выделяет буферы, кладёт адреса в стаб
3) cudaMemcpy(devPtr, hostStub, ...)  байтовая копия стаба → адреса уехали
4) constructDeviceObjectKernel<<<1,1>>>     placement new поверх копии → чинит vtable
```

Сначала копия, **потом** конструктор. Иначе конструктор, отработавший первым,
был бы затёрт копией стаба вместе с только что записанной устройственной vtable.

Но раз конструктор выполняется **после** того, как адреса уже приехали, из этого
следует жёсткое правило, которое легко нарушить:

> **Конструктор такого класса не имеет права трогать ни один указатель на
> буфер.** Только value-поля (размеры, флаги). Строчка вида `keys_(nullptr)` в
> списке инициализации молча затрёт адрес, выделенный на шаге 2, и всё
> развалится в ядре.

Это записано в комментарии к каждому такому классу — теперь понятно, почему.

### 1.4. И, наконец: хостовую vtable может выпустить не всякий компилятор

`key()` объявлена только как `__device__`. Хостовая vtable класса всё равно
нужна — она есть у `hostStub`, ведь это обычный хостовой объект. Но что положить
в её слот для `key()`, если хостовой версии `key()` не существует?

* **nvcc** — придумывает заглушку и vtable выпускает;
* **`nvc++ -cuda`** (а именно им собирается модель химии OpenFOAM) — не
  придумывает и останавливается с ошибкой «`key` не определена в vtable».

Ключевой момент: vtable выпускается **в той единице трансляции, которая создаёт
объект**. Значит, достаточно не позволять чужому компилятору создавать стаб:

```cpp
// в .cu, который компилирует nvcc — здесь и рождается хостовая vtable
StiffnessBalancer* stub = StiffnessBalancer::createStub(...);

// у вызывающего кода — только указатель, ему vtable выпускать не нужно
kodes::Balancer* stub;
```

Поэтому у каждого класса есть не два, а **четыре** статических метода:
`create`/`destroy` (объект на устройстве) и `createStub`/`destroyStub` (двойник
на хосте).

## 2. Контракт: что должен предоставить класс

Всё вышеперечисленное написано **один раз** в `Factory/device_object.cuh`. Чтобы
класс можно было строить этими шаблонами, от него требуется ровно три вещи:

```cpp
class MyBalancer : public kodes::Balancer
{
public:
    // 1. Конструктор с ровно такой сигнатурой — одинаковой у всех
    //    устройственных объектов библиотеки. Только value-поля! (см. 1.3)
    __device__ __host__
    MyBalancer(label batchSize, label scratchSize, label systemSize, label parameterSize);

    // 2. Хостовые allocate/deallocate — cudaMalloc/cudaFree в собственные поля.
    //    Наследник сначала вызывает версию базового класса, потом свою.
    __host__ void allocate();
    __host__ void deallocate();

    // 3. placement new на устройстве (обычно уже унаследован от базы)
    __device__ static void* operator new(size_t, void* ptr) { return ptr; }
};
```

Если выделять нечего — `allocate()` наследуется пустой, и класс строится теми же
самыми вызовами.

### Почему `allocate()` не виртуальная

Это не забывчивость. Фабрика — **шаблон**, инстанцируемый конкретным типом:

```cpp
template<class T>
__host__ T* createDeviceObject(..., T* hostStub)
{
    hostStub->allocate();       // T известен, вызов разрешается статически
    ...
}
```

Получается разделение, ради которого паттерн и существует:

* **на хосте — статический полиморфизм** (шаблон подставляет нужный `allocate`);
* **на устройстве — динамический** (ядро зовёт `key()`/`step()` через vtable).

Хостовая vtable нужна только для деструктора, и ни один виртуальный вызов на
хосте паттерн не делает.

### Что пишется в `.cu` класса

Одна строка:

```cpp
#include "MyBalancer.cuh"

KODES_DEFINE_DEVICE_OBJECT(kodes::MyBalancer)
```

Макрос разворачивается в те самые четыре метода, каждый из которых — вызов
соответствующего шаблона. Объявления в заголовке — тоже одна строка,
`KODES_DECLARE_DEVICE_OBJECT(MyBalancer)`.

Этот `.cu` **никогда не включается вызывающим кодом**: именно в нём запускаются
ядра конструктора и деструктора и именно в нём выпускается хостовая vtable.

Если классу нужно что-то сверх этих четырёх шагов, он пишет свой `create()`
руками и зовёт `createDeviceObject()` внутри — так, например,
`SeulexDeviceResources::allocate()` дополнительно заливает таблицы
экстраполяции в `__constant__`-память.

## 3. Выбор по имени: таблица типов

Построить объект мы теперь умеем. Осталось выбрать, **какой**.

Соблазнительно сделать это хостовыми виртуальными функциями — но тогда чужой
компилятор должен был бы согласиться с nvcc о раскладке vtable, в которой есть
слот для несуществующей на хосте `key()`. Это лишний риск на ровном месте.

Вместо этого один конкретный класс сводится к набору **обычных указателей на
функции** (`type_table.cuh`):

```cpp
template<class Base>
struct TypeEntry
{
    const char* name;

    Base* (*create)(label, label, label, label, Base* stub);
    Base* (*createStub)(label, label, label, label);
    void  (*destroy)(Base*, Base*);
    void  (*destroyStub)(Base*);

    size_t (*scratchBytesPerThread)(label systemSize, label parameterSize);
    size_t (*stateBytesPerSystem)(label systemSize, label parameterSize);
};
```

Указатель на функцию — это просто адрес. Никакой vtable, никаких требований к
ABI сверх обычных. Поэтому таблицу может использовать **любой** компилятор, хотя
классы в ней виртуальны только на устройстве.

Заполняется строка таблицы шаблоном `typeEntry<Base, Derived>("имя")`: внутри
него безкаптурные лямбды (они конвертируются в указатели на функции) приводят
`Base*` обратно к `Derived*` и зовут статику нужного класса.

Две последние строчки — почему одна таблица вообще может держать классы,
не имеющие между собой ничего общего: **каждый умеет ответить, во что он
обойдётся** — сколько памяти устройства на один резидентный поток и на одну
систему партии. `planLaunch()` складывает эти числа **до того**, как хоть
что-нибудь создано, — а иначе и нельзя, ведь размеры партии и сетки как раз из
этого расчёта и получаются.

Сами таблицы — по одной на абстрактную базу, в `.cu` библиотеки:

```cpp
// src/Balancer/balancer_table.cu
static const TypeEntry<Balancer> table[] =
{
    typeEntry<Balancer, TemperatureBalancer>("temperature"),
    typeEntry<Balancer, RHSNormBalancer>("rhsNorm"),
    typeEntry<Balancer, StiffnessBalancer>("stiffness")
};
```

```cpp
// src/Integrator/IntegrationMethods/method_table.cu — здесь в одной строке
// метод и хранилище, потому что выбирать их порознь нельзя: Seulex::step()
// приводит DeviceResources* к SeulexDeviceResources*
static const MethodType table[] =
{
    { "seulex",
      typeEntry<IntegrationMethod, Seulex>("seulex"),
      typeEntry<DeviceResources, SeulexDeviceResources>("seulexResources") },

    { "euler",
      typeEntry<IntegrationMethod, Euler>("euler"),
      typeEntry<DeviceResources, EulerDeviceResources>("eulerResources") }
};
```

Имя, которого в таблице нет, обрывает запуск сообщением со списком известных —
и обрывает его в конструкторе `Settings`, то есть до первого `cudaMalloc`.

## 4. `Handle` — кто всё это удаляет

Объект на устройстве и его стаб — две отдельные вещи, и удалять их надо теми же
методами того же класса, которым они созданы. Помнить об этом вызывающему коду
не нужно: `Handle<Base>` держит и то и другое вместе с указателем на строку
таблицы, из которой они сделаны, и в деструкторе зовёт `destroy`/`destroyStub`
именно оттуда.

```cpp
kodes::Handle<kodes::Balancer> balancing = kodes::newBalancer
(
    "stiffness", batchSize, scratchSize, systemSize, parameterSize
);

solver.setBalancer(balancing.device(), balancing.host());
// деструктор Handle сам вернёт обе половины тому, кто их сделал
```

`device()` — объект, на котором диспетчеризуются ядра. `host()` — стаб, через
который идут хостовые вызовы (`balance()`, `order()`, буферы для `Operator`).

Для балансировщика есть особый случай: имя `"none"` даёт **пустой** handle
(`device()` и `host()` — нули), и `Integrator::setBalancer(nullptr, nullptr)`
понимает это как «партия интегрируется в том порядке, в каком её скопировали».

## 5. Полная картина: три копии объекта

```
              ХОСТ                                    УСТРОЙСТВО
   ┌───────────────────────────┐          ┌──────────────────────────────┐
   │ Handle<Balancer>          │          │                              │
   │   type_ ──▶ строка таблицы│          │                              │
   │   host_ ──┐               │          │                              │
   │   device_─┼───────────────┼─────────▶│ devObject                    │
   └───────────┼───────────────┘          │   vtable → устройственная    │
               │                          │   keys_  ──────────┐         │
               ▼                          │   order_ ────────┐ │         │
   ┌───────────────────────────┐          └──────────────────┼─┼─────────┘
   │ hostStub                  │                             │ │
   │   vtable → хостовая       │          ┌──────────────────▼─▼─────────┐
   │   keys_  ─────────────────┼─────────▶│  буферы, cudaMalloc          │
   │   order_ ─────────────────┼─────────▶│                              │
   └───────────────────────────┘          └──────────────────────────────┘
      те же адреса, что и в devObject:
      это байтовая копия одного и того же
```

Одни и те же буферы видны с обеих сторон: `Operator` читает их адреса из стаба,
ядра — из объекта на устройстве.

## 6. Как добавить свой класс

Балансировщик — четыре шага:

1. `src/Balancer/MyBalancer.cuh`: наследник `Balancer` с конструктором из четырёх
   аргументов, `key()`, парой `stateBytesPerSystem`/`scratchBytesPerThread` и
   строкой `KODES_DECLARE_DEVICE_OBJECT(MyBalancer)`.
2. `src/Balancer/MyBalancer.cu`: `KODES_DEFINE_DEVICE_OBJECT(kodes::MyBalancer)`.
3. Одна строка в `src/Balancer/balancer_table.cu`.
4. Одна строка в `cmake/kodes.cmake`.

Метод интегрирования — то же самое, но наследник `IntegrationMethod` с `step()`,
и в строке таблицы рядом указывается его класс хранилища. Если методу нужны свои
временные массивы — сначала наследник `DeviceResources` с собственными
`allocate()`/`deallocate()`, по тому же паттерну.

После этого новое имя работает в `grimech.json` без единой правки в вызывающем
коде.

## 7. Чего этот паттерн стоит

Виртуальный вызов на устройстве не инлайнится: компилятор обязан соблюсти ABI и
завести кадр стека. Для `step()` это неважно — вызов происходит один раз на шаг
системы, против шага, который факторизует матрицу `systemSize × systemSize`. И
ядро всё равно уже делало такие вызовы: `ODESystem::derivatives()` и
`ODESystem::jacobian()` виртуальны с самого начала, а при раздельной компиляции
(`CUDA_SEPARABLE_COMPILATION ON`) девиртуализовать их всё равно было нечем.

Что действительно поменялось — `planLaunch()` теперь спрашивает занятость одного
ядра `solveKernel` на все методы сразу, а не отдельной инстанциации на каждый.
Раньше в ядро инлайнился весь `Seulex::step`, и занятость считалась по его
регистрам; теперь ядро само по себе маленькое. Если после замеров окажется, что
сетка выходит крупнее, чем устройство реально держит резидентной, — лишнее место
уходит в scratch-слоты, и это лечится `"share": "half"` или явными
`concurrentSystems`/`batchSize` в файле настроек.
